# Деплой tg_bot

Один репозиторий обслуживает два разных типа деплоя:

- **деплой клиента** — магазин и админка одного бота. У него есть `BOT_ID`,
  и в базу он ходит ключом арендатора: RLS отдаёт только его строки.
- **панель оператора** — `CONTROL_PLANE=1`. Своей строки в `bots` у неё нет,
  магазин и админка клиента там отключены (см. `assertTenantDeployment`).

Переменные у них разные, поэтому и таблицы ниже разные.

---

## Переменные деплоя клиента

### Обязательные

| Переменная                      | Описание                                                                                                                                           |
| ------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `BOT_ID`                        | UUID строки клиента в таблице `bots`. Без него деплой не знает, чей он.                                                                            |
| `SUPABASE_TENANT_KEY`           | JWT с `role: tenant_bot` и `bot_id`. Выпускается `scripts/mint-tenant-key.mjs`. Именно он ограничивает деплой своими строками.                     |
| `SUPABASE_URL`                  | URL проекта Supabase.                                                                                                                              |
| `SUPABASE_PUBLISHABLE_KEY`      | Anon key. Идёт в заголовок `apikey`.                                                                                                               |
| `SUPABASE_SERVICE_ROLE_KEY`     | Нужен шлюзу Supabase как ключ проекта. Роль при этом берётся из `SUPABASE_TENANT_KEY`, а не отсюда.                                                |
| `VITE_SUPABASE_URL`             | То же значение, что `SUPABASE_URL`. Читается **в браузере**.                                                                                       |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | То же, что `SUPABASE_PUBLISHABLE_KEY`, тоже для браузера.                                                                                          |
| `TELEGRAM_BOT_TOKEN`            | Токен основного бота (@BotFather).                                                                                                                 |
| `ADMIN_USERNAME`                | Логин в админку. Без него (и без `ADMIN_PASSWORD`) вход отключён — значения по умолчанию `admin`/`admin` больше нет намеренно.                     |
| `ADMIN_PASSWORD`                | Пароль в админку. Без него (и без `ADMIN_USERNAME`) вход отключён тем же образом.                                                                  |
| `SESSION_SECRET`                | Ключ подписи cookie сессии. **Без него (или короче 32 символов) вход в админку отключён явной ошибкой** — раньше подставлялось общеизвестное значение из исходников, и cookie можно было подделать; теперь так не будет молча. |
| `PUBLIC_APP_URL`                | Публичный адрес деплоя, например `https://client.vercel.app`. По нему ставится webhook.                                                            |
| `CRON_SECRET`                   | Секрет для `/api/cron/*`.                                                                                                                          |

> `VITE_*` подставляются **в момент сборки**. Добавили их после деплоя — нужен
> пересбор, иначе в браузерном бандле их не будет.

> **Почему в репозитории нет `.env.example`.** Vercel читает этот файл при
> импорте проекта из Git и заранее заполняет форму переменных — вместе с
> подставными значениями вроде `https://your-project.supabase.co`. Их
> приходилось вычищать руками перед тем, как вставить настоящий блок, а
> заодно файл успел отстать от жизни: в нём не было ни `SUPABASE_TENANT_KEY`,
> ни `ADMIN_PASSWORD`. Список переменных живёт здесь, а готовый блок для
> вставки выдаёт панель. Не заводите `.env.example` заново.

> Значения типа Sensitive в интерфейсе Vercel показываются замаскированными
> (`eyJhbGci••••`). **Копировать их оттуда нельзя** — вставится буквально
> символ «•» (U+2022), и деплой упадёт с `Cannot convert argument to a
ByteString`. Берите значение из первоисточника.

## Переменные панели оператора

| Переменная                                                                       | Описание                                                                                         |
| -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `CONTROL_PLANE`                                                                  | `1`. Включает панель и **выключает** магазин с админкой клиента.                                 |
| `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`                                      | Панель работает поверх всех клиентов, поэтому здесь ключ арендатора не подходит.                 |
| `SUPABASE_PUBLISHABLE_KEY`, `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY` |                                                                                                  |
| `SUPABASE_JWT_SECRET`                                                            | Нужен только мастеру подключения: им подписывается `SUPABASE_TENANT_KEY` новому клиенту.         |
| `OPERATOR_USERNAME`, `OPERATOR_PASSWORD`                                         | Вход в панель. Если не заданы, вход не работает вовсе — значения по умолчанию тут нет намеренно. |
| `OPERATOR_SESSION_SECRET`                                                        | Ключ подписи cookie оператора. Как и `SESSION_SECRET`, без него (или короче 32 символов) вход отключён явной ошибкой, а не общеизвестным значением. |
| `CRON_SECRET`                                                                    | Секрет для суточного прохода по подпискам.                                                       |

Токенов ботов у панели нет **намеренно**: рассылку владельцам она отправляет
не сама, а запросом `POST {bots.app_url}/api/internal/notify-owner` в деплой
самого клиента, с заголовком `x-internal-secret` (значение — `bots.internal_secret`,
оно хранится в базе, а не в переменных окружения). Если деплой клиента лежит,
сообщение не доставлено — и панель показывает это, а не проглатывает.

## Подключение нового клиента

1. Панель → «Подключить клиента». Мастер проверяет токен через `getMe`,
   заводит строку в `bots` и печатает готовый блок переменных.
   **Токен нигде не сохраняется** — он нужен только для проверки.
2. Создать проект в Vercel из этого репозитория, вставить переменные.
3. Дождаться сборки, открыть `/login` — должно отвечать 200.
4. Поставить webhook: панель → карточка клиента → «Переустановить webhook»
   (панель попросит об этом сам деплой клиента, токен ей не нужен).
5. Проверить в Telegram командой `/start`.

Если бот раньше жил на другом деплое, старый проект надо **удалить**. Пока он
жив, его собственный cron `ensure-webhook` пытается забрать бота обратно.
Защита от этого есть — деплой ставит webhook, только если `bots.app_url`
совпадает с его собственным адресом (`ownsWebhook`), — но старый проект всё
равно тратит вызовы и путает диагностику.

## Cron

На **Vercel Pro** расписание задаётся нативно, прямо в `vercel.json` →
`crons`, и деплой сам регистрирует задания при каждом деплое — отдельно
настраивать ничего не нужно, кроме `CRON_SECRET` (см. выше). Vercel сам
подставляет `Authorization: Bearer $CRON_SECRET` в каждый такой вызов, если
переменная окружения называется ровно `CRON_SECRET`.

> На тарифе **Hobby** так не работало: нативный cron разрешал не чаще раза в
> сутки, поэтому расписание держал внешний сервис (например, cron-job.org).
> Задачи ниже раньше были собраны в одном `/api/cron/broadcast` ровно по
> этой причине — второй внешний вызов ради одной задачи не окупался. На Pro
> лимита на число заданий практически нет, задачи разведены по смыслу и у
> каждой своё расписание. Если внешний cron всё ещё настроен — его можно
> отключить, нативный делает то же самое надёжнее и без лишнего вызова
> наружу; на переходный период оставить оба не страшно, эндпоинты
> идемпотентны.
>
> **Важно для `/api/public/vip/cron`:** он появился в `vercel.json` позже
> остальных пяти — до этого держался только на внешнем cron-job.org и нигде
> не был задокументирован. Если у клиента с VIP-модулем всё ещё настроен
> старый внешний вызов на этот путь — можно отключать, но **сначала
> убедиться**, что нативный из `vercel.json` реально дошёл до продакшена
> (задеплоен), иначе окно между отключением старого и раскаткой нового
> оставит VIP-подписки без проверки истечения.

`vercel.json` одинаков для всех деплоев этого репозитория (семь клиентских и
панель — число сверено с живой базой в рамках ревизии кондитерской ветки),
поэтому каждый роут ниже сам решает, кому он относится: клиентские
задачи отвечают `404` на деплое панели (`CONTROL_PLANE=1`) и наоборот — без
этого нативный cron дёргал бы клиентские задачи и на панели тоже, без
`BOT_ID` им там нечего делать.

| Роут | Расписание | Что делает |
| --- | --- | --- |
| `/api/cron/broadcast` | раз в минуту | Рассылка (порции по 25), выдача отложенных заказов, подтверждение вебхука. Самая частая и самая денежная задача — остальные вынесены из неё, чтобы не делить с ней бюджет запроса. |
| `/api/cron/zernio-retry` | раз в 2 минуты | Добор зависших `pending`-событий Instagram (Zernio) — раньше добирались раз в 1–2 минуты заодно с рассылкой, теперь независимо. |
| `/api/cron/zernio-logs-prune` | раз в сутки (03:00 UTC) | Ретеншн `zernio_logs` (`ZERNIO_LOG_RETENTION_DAYS`). Не нужна чаще — таблица растёт медленно относительно окна хранения. |
| `/api/cron/ensure-webhook` | раз в час | Независимая подстраховка сверх той же проверки, что и так идёт на каждый тик `/api/cron/broadcast`. |
| `/api/cron/manager-chat-prune` | раз в сутки (03:15 UTC) | Ретеншн истории «Чат с продавцом» (перехват оператором) — старые записи удаляются, чтобы таблица не росла бесконечно. |
| `/api/cron/misc-retention` | раз в сутки (03:30 UTC) | Ретеншн `admin_login_attempts`, `operator_login_attempts`, `bot_events`, `broadcast_recipients` (Блок 3.2). |
| `/api/cron/cart-reminder` | раз в 30 минут | Напоминание о брошенной корзине (см. `cart_reminder_hours` в настройках) — «Открыть корзину» покупателю, который добавил товар и надолго замолчал. |
| `/api/cron/fulfillment-reminder` | раз в час | Ниши (физические товары): напоминание за сутки до `fulfillment_at` — и покупателю, и продавцу. Без неё дата получения физического заказа никак не подсвечивается заранее ни одной из сторон. |
| `/api/public/vip/cron` | раз в час (:30) | Только для клиентов с модулем VIP. Восстанавливает вебхуки shop+VIP-бота (`ensureDidWebhooks`) и гоняет `runVipCronJob`: предупреждает подписчиков за `vip_warn_days`/`vip_warn_days_2` дней и исключает из VIP-группы тех, у кого истёк срок. Без этой задачи VIP-подписки не истекают сами — ни увольнение из группы, ни напоминания. |
| `/api/operator-cron/subscriptions` | раз в сутки (04:00 UTC), только панель | Обход подписок: предупреждает владельцев о скором окончании оплаты, применяет `bots.settings.on_overdue`. Идемпотентен — повторный вызов в тот же день ничего не продублирует. |
| `/api/operator-cron/retention` | раз в сутки (03:45 UTC), только панель | Ретеншн операторских логов/истории панели (её собственные таблицы, не клиентские). |
| `/api/operator-cron/health-snapshot` | раз в 15 минут, только панель | Снимок состояния клиентских деплоев для «Истории падений бота» в панели оператора. |

Ручной вызов (для проверки, что секрет верный и логика работает):

```
GET https://your-app.vercel.app/api/cron/broadcast?secret=YOUR_CRON_SECRET
GET https://your-app.vercel.app/api/public/vip/cron?secret=YOUR_CRON_SECRET
GET https://panel.vercel.app/api/operator-cron/subscriptions?secret=YOUR_CRON_SECRET
```

> **`maxDuration` вебхука Zernio отдельно не поднят этой правкой.** Сборка
> идёт через Nitro/`vercel.json` в формате Build Output API v3, и без живого
> деплоя нельзя достоверно проверить, что именно даст ожидаемый эффект —
> правка per-route конфигурации Nitro или ползунок «Function Max Duration» в
> Vercel Dashboard → Settings → Functions. Стоит сделать отдельным шагом с
> проверкой на реальном деплое: на Pro доступно кратно больше времени, чем на
> Hobby, и это снижает частоту, с которой `waitUntil`-обработка вебхука вообще
> не успевает записать статус (см. «69 потерянных Instagram-событий» в
> `ANALYSIS.md`) — крон-добор из таблицы выше стал страховкой уже сейчас, а
> увеличенный `maxDuration` уменьшит саму частоту, с которой эта страховка
> нужна.

## Модуль рассылки — smoke-проверка

1. В настройках бота задан `admin_chat_id` (ваш Telegram ID).
2. Админка → «Рассылка», текст, аудитория «Тест (admin Telegram ID)».
3. «Отправить себе (тест)» → сообщение приходит в Telegram.
4. Аудитория «Все пользователи» → «Запустить рассылку».
5. Статус идёт `В очереди` → `Отправляется` → `Завершена`.
6. Счётчики sent/failed/blocked в истории сходятся.
7. Отмена: запустить рассылку и нажать «Отменить» до завершения.
