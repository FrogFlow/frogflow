# Объединение клиентов в одну базу — порядок работ

Все боты переезжают в базу этого проекта (`fnwksbasxakktscdjlfp`). У неё уже
есть таблица `bots` и колонки `bot_id` — начатая ранее и не доведённая до конца
мультитенантность.

Порядок шагов важен: часть изменений ломающие, и применять их можно только
после того, как задеплоен соответствующий код.

---

## Как устроена изоляция

Клиент не должен видеть чужие данные. В коде ~157 обращений к БД, и полагаться
на то, что в каждом не забыт фильтр, нельзя — одна ошибка означает утечку.
Поэтому изоляцию обеспечивает Postgres:

- у каждого деплоя свой ключ `SUPABASE_TENANT_KEY` с зашитым `bot_id`;
- PostgREST переключается в роль `tenant_bot`, RLS-политики отсекают чужие строки;
- триггер `force_bot_id` проставляет `bot_id` при вставке — подделать из
  приложения нельзя.

Запросы в коде при этом **не меняются**. Хранилище файлов работает под
service_role (`.storage` в клиенте выведен из-под изоляции), поэтому бакеты
общие — защита от кросс-клиентского удаления сделана в самом коде сброса.

Откат на любом шаге: убрать `SUPABASE_TENANT_KEY` — деплой возвращается к
прежнему доступу без изоляции.

## Шаги

### 1. ФАЗА 1 — фундамент (безопасно, бот работает) ✅ ВЫПОЛНЕНО

`MIGRATION-01-tenancy-foundation.sql` — только добавляет колонки и таблицы.

### 2. ФАЗА 3 — нумерация заказов (безопасно, до деплоя!)

`MIGRATION-03-per-tenant-order-numbers.sql`.

Именно до деплоя: новый код запрашивает `order_no`, а PostgREST на
несуществующую колонку отвечает ошибкой, а не пустым значением — выдача
заказов сломалась бы. Со старым кодом миграция полностью совместима: он про
`order_no` не знает, а триггер проставляет номер сам.

Проверка (нумерация Анастасии должна продолжиться, не начаться заново):

    SELECT bot_id, min(order_no), max(order_no), count(*) FROM orders GROUP BY bot_id;
    SELECT * FROM order_counters;

### 3. Задеплоить код

Переменная `BOT_ID=0bac1f86-5231-4e57-838d-2faa44d427e7` уже добавлена.
`SUPABASE_TENANT_KEY` пока **не** ставить — изоляции в БД ещё нет.

Что меняется: безопасный сброс данных, показ `order_no` покупателю,
разделение подключения к БД и к хранилищу.

**Проверить после деплоя:** каталог, оформление заказа (номер должен
продолжить прежний ряд), приём чека, выдача файлов, админ-панель.

### 4. Обновить типы

    SUPABASE_URL=… SUPABASE_SERVICE_ROLE_KEY=… node scripts/sync-db-types.mjs

### 5. ФАЗА 2 — изоляция

`MIGRATION-02-tenant-isolation.sql`. Деплои ходят под service_role, который
обходит RLS, поэтому поведение не меняется — политики просто начинают
существовать.

### 6. Включить изоляцию для бота Анастасии

Добавить в Vercel выпущенный `SUPABASE_TENANT_KEY`, передеплоить и пройти
тот же чек-лист, что в шаге 3. Любая проблема — удалить переменную и
передеплоить, это мгновенный откат.

После успешной проверки снять временный `DEFAULT` с `bot_id`:

    -- по каждой таблице из Фазы 1
    ALTER TABLE public.<таблица> ALTER COLUMN bot_id DROP DEFAULT;

### 7. ФАЗА 4 — уникальность в пределах бота

`MIGRATION-04-scope-unique-indexes.sql`.

Пока клиент один, глобальные уникальные индексы незаметны. Со вторым они
начинают запрещать законное: `idx_bot_users_telegram_id_unique` не даёт одному
человеку в Telegram быть покупателем у двух клиентов — на этом и споткнулся
первый перенос. Миграция находит **все** такие индексы и пересоздаёт их с
`bot_id` в начале.

### 8. Перенос остальных клиентов

Записи в `bots` уже созданы:

| клиент                      | bot_id                                 |
| --------------------------- | -------------------------------------- |
| Анастасия (Educational Bot) | `0bac1f86-5231-4e57-838d-2faa44d427e7` |
| SALTANAT                    | `de44b934-c8db-47ac-9aa9-535c762cf8c7` |
| Print KZ Art                | `89d155d1-91e1-4c2d-981e-43741a0badc3` |

Для каждого:

1. правки в его репозитории — **обязательно до переключения**:
   сброс данных (иначе сотрёт файлы всех клиентов), `category_ids` как `jsonb`,
   поддержка ключа арендатора в клиенте Supabase;
2. перенос строк из его базы с подстановкой нового `bot_id`
   (`category_ids` там `uuid[]`, здесь `jsonb` — конвертируется при вставке);
3. копирование файлов из его Storage в общий (имена не пересекаются —
   генерируются как `timestamp-random.ext`);
4. свой `SUPABASE_TENANT_KEY` + `BOT_ID` в его Vercel, `SUPABASE_URL` меняется
   на общий.

Объёмы небольшие: print_kz_art — 27 товаров / 3 заказа / 643 МБ файлов,
saltanat — 3 товара / 5 заказов / 88 МБ.

## Что учесть

- **`increment_broadcast_counts`** — код вызывает эту RPC, но в базе её нет:
  счётчики рассылок молча не обновляются. Существующая проблема, не связана с
  переездом.
- **`reset_orders_sequence`** больше не вызывается: последовательность `id`
  общая, откат счётчика выдал бы номера, уже занятые другими клиентами.
- **Файлы в общих бакетах** — новые ключи (`product-files`, `product-images`,
  `payment-proofs`, `broadcast-images`) с этого момента пишутся с префиксом
  `{bot_id}/`, и раздача (`/api/public/img/$`, `/api/admin/file/$`) сверяет
  его с `BOT_ID` текущего деплоя (`src/lib/tenant-storage-key.server.ts`).
  Ключи без префикса — файлы, залитые раньше, — по-прежнему обслуживаются как
  есть: их не переименовать задним числом, не сломав уже выданные ссылки.
  `storage.objects` в Supabase не поддерживает RLS по кастомной роли (не наша
  БД устроена по-другому — сам PostgREST для Storage не резолвит `tenant_bot`,
  см. `client.server.ts`), так что изоляция здесь на разметке путей, а не на
  политике.
- **`DEFAULT bot_id`**, поставленный в Фазе 1, снять после шага 6: пока он есть,
  строка без явного `bot_id` молча припишется существующему боту.

## 9. Панель управления клиентами — Фаза 0

Задание целиком в `CONTROL-PLANE-PLAN.md`. Первый шаг — предохранитель, а не
код: `MIGRATION-08-operator-foundations.sql`. Без него включение Фазы 1 (чтение
`bots.modules` во время выполнения вместо сборочных `VITE_FEATURE_*`) молча
выключит модули, которых нет в текущем разнобое ключей у пяти клиентов.

Делает: нормализует `bots.modules` до единого набора из 13 ключей, зануляет
`bots.bot_token` (у Анастасии там живой токен), добавляет колонки под панель
(`app_url`, `internal_secret`, `owner_*`, `paused_message`, `notes`),
расширяет `status` до `active|paused|suspended`, проставляет дефолт
`bots.settings` под политику при неоплате, заводит `bot_events` и
`operator_broadcasts` с RLS, закрытым для `tenant_bot`.

Применять вручную в Supabase SQL Editor — как и MIGRATION-01…07: DDL через
`SUPABASE_SERVICE_ROLE_KEY` (это ключ Data API, не пароль Postgres)
не выполнить. Проверки — в конце файла миграции.

После применения останется вручную: заполнить `app_url` пятью адресами
деплоев (не угадываются, известны только оператору).
