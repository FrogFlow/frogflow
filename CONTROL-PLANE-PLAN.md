# Панель управления клиентами — проектный план

Своя админка поверх всех клиентских ботов: список клиентов, включение модулей
одним флажком, стоп/старт бота, связь с владельцами, подключение новых
клиентов. Живёт в этом же репозитории, но разворачивается отдельным проектом
Vercel и недоступна из клиентских деплоев.

Документ — задание на реализацию. Решения приняты, обоснования приведены там,
где иначе они выглядели бы произвольными. Реализовывать можно по фазам, каждая
фаза самостоятельно полезна.

---

## 0. Что нужно знать до начала

Три факта, установленных при обследовании, — они определяют половину решений.

**1. У каждого клиентского деплоя есть `SUPABASE_SERVICE_ROLE_KEY.**
Он нужен для Storage (бакеты общие, `.storage` намеренно выведен из-под
изоляции). Это значит: если код панели попадёт в клиентскую сборку и там
найдётся способ его вызвать — RLS не спасёт, service_role видит всё. Отсюда
трёхслойная защита в §2, а не «просто проверим сессию».

**2. `bots.modules` не соответствует действительности и не унифицирован.**

| Клиент | ключи в БД сейчас |
|---|---|
| Анастасия | `shop, coupons, courses, referral, instagram, broadcasts, ai_assistant, multi_currency, crm_integration` |
| Салтанат / Print KZ | `vip, shop, blocked, instagram, multi_currency` |
| Дидактика | `vip, shop, instagram, broadcasts, multi_currency` |
| Развивашка | `vip, shop, instagram, broadcasts, multi_currency` |

Наборы ключей разные, часть значений — про модули, которых в коде нет
(`ai_assistant`, `crm_integration`). Пока флаги читаются из кода, это никого не
трогает. В момент переключения на чтение из БД **каждое расхождение станет
пропавшей функцией у живого клиента.** Поэтому Фаза 0 — нормализация, и только
потом Фаза 1.

**3. `bots.bot_token` у Анастасии содержит настоящий токен бота.**
Не заглушку — рабочий `8956271941:AAG…`. Токен Telegram даёт полный контроль
над ботом: читать переписки, слать сообщения, сменить вебхук. Хранить пять
таких в одной таблице, к которой ходит веб-панель, — плохая идея. В §5 описан
способ обойтись без этого, а сам столбец надо очистить (Фаза 0).

## 1. Общая схема

```
┌──────────────────────────┐        ┌──────────────────────────────┐
│  Панель управления       │        │  Клиентские деплои (×5)      │
│  Vercel-проект «operator»│        │  Vercel-проекты клиентов     │
│  CONTROL_PLANE=1         │        │  CONTROL_PLANE не задан      │
│  service_role + JWT secret│       │  SUPABASE_TENANT_KEY         │
└───────────┬──────────────┘        └──────────┬───────────────────┘
            │                                   │
            │ пишет bots.modules / status       │ читает свою строку bots
            ▼                                   ▼
      ┌───────────────────────────────────────────────┐
      │      Общая база Supabase (fnwksbasx…)         │
      └───────────────────────────────────────────────┘
            │
            │ HTTPS + общий секрет, для действий,
            │ требующих токена бота (§5)
            └──────────────────► /api/internal/* клиентского деплоя
```

Один репозиторий, шесть проектов Vercel. Панель отличается от клиентского
деплоя ровно одной переменной окружения.

## 2. Изоляция панели — три слоя

Код панели физически присутствует в бандле каждого клиента (один репозиторий).
Поэтому недостаточно спрятать ссылку — нужны настоящие замки.

**Слой 1 — переменная окружения.** `CONTROL_PLANE=1` только на вашем проекте.

**Слой 2 — отдельная сессия.** Своё имя куки и свой секрет
(`OPERATOR_SESSION_SECRET`), не пересекающиеся с клиентской админкой. Иначе
администратор клиента, залогиненный в своей панели, технически предъявлял бы
валидную куку и вашей.

**Слой 3 — проверка в каждой серверной функции.**

```ts
// src/lib/operator/guard.server.ts
export async function requireOperator() {
  if (process.env.CONTROL_PLANE !== "1") {
    // Тот же ответ, что и для несуществующего пути: клиентский деплой не
    // должен даже подтверждать, что такая функция существует.
    throw new Error("Not found");
  }
  const s = await getOperatorSession();
  if (s.data.authed !== true) throw new Error("Unauthorized");
  return s;
}
```

**Первой строкой каждой** серверной функции в `src/lib/operator/*`. Не в
роутере, не в middleware — в самой функции: серверные функции TanStack Start
вызываются по HTTP напрямую, guard в `beforeLoad` их не прикрывает.

Роуты `/operator/*` дополнительно делают `beforeLoad` → `throw notFound()`,
если серверная проверка не прошла — чтобы на клиентском деплое путь выглядел
несуществующим.

**Сверх кода:** на Vercel-проекте панели включить Deployment Protection
(пароль или SSO). Панель не должна быть публично доступна в принципе — это
дешевле любой доработки кода.

### 2.1. Переменные проекта панели — проверено запуском

| Переменная | Зачем |
|---|---|
| `CONTROL_PLANE=1` | слой 1: без неё весь `/operator/*` отвечает 404 |
| `OPERATOR_SESSION_SECRET` | своя сессия, не пересекается с админкой клиентов |
| `OPERATOR_USERNAME`, `OPERATOR_PASSWORD` | вход; без них логин отвечает явной ошибкой |
| `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` | доступ к общей базе |
| `SUPABASE_PUBLISHABLE_KEY` | SSR-мидлварь создаёт браузерный клиент на каждый запрос |
| `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY` | **нужны на сборке**, см. ниже |
| `SUPABASE_JWT_SECRET` | только для подключения клиента (выпуск ключа арендатора) |
| `CRON_SECRET` | только для ежедневного обхода подписок |

**`BOT_ID` на панели задавать нельзя.** Панель не арендатор, своей строки в
`bots` у неё нет. А `client.server.ts` намеренно падает, если `BOT_ID` задан
без `SUPABASE_TENANT_KEY`, — защита от деплоя, который молча ходит под
service_role в обход RLS.

**Грабли, найденные при проверке: `VITE_*` вшиваются на этапе сборки.**
Серверный код умеет откатиться на `SUPABASE_URL`/`SUPABASE_PUBLISHABLE_KEY`
из окружения, а браузерный — нет: у него значения зашиты в бандл. Если
`VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY` не заданы **в момент
сборки**, страница входа открывается, но при нажатии «Войти» показывает
`Missing Supabase environment variable(s)`. Задать переменные и передеплоить
— пересборка обязательна, простого рестарта мало.

Проверено на собранном бандле: у панели `/operator` → 307 на логин, после
входа виден список из 5 клиентов; у деплоя без `CONTROL_PLANE` те же пути
отвечают 404, а прямой вызов серверной функции панели — «Not found» даже с
действительной операторской кукой (без неё, но на самой панели, — 
«Unauthorized»).

## 3. Реестр модулей — сердце всей затеи

Требование «функция уже готова в коде, нужен только флажок» реализуется одним
файлом-каталогом. Он же источник данных для интерфейса панели: добавили запись
— тумблер появился у всех клиентов сам.

```ts
// src/lib/modules/registry.ts
export type ModuleKey = keyof typeof MODULES;

export type ModuleDef = {
  title: string;            // как показывать в панели
  group: string;            // группировка, совпадает с разделами прайса
  price: number | null;     // ₸, из прайса; null — входит в базу
  status: "available" | "planned";  // planned — записан в прайсе, кода ещё нет
  requires?: ModuleKey[];   // зависимости (напр. dm_shop требует instagram)
  note?: string;            // подсказка оператору
};

export const MODULES = {
  shop:            { title: "Магазин",              group: "База",     price: null, status: "available" },
  vip:             { title: "VIP-подписки",         group: "Каталог",  price: 22000, status: "available" },
  blocked:         { title: "Блокировка",           group: "Сервис",   price: 14000, status: "available" },
  instagram:       { title: "Instagram-автоматизация", group: "Instagram", price: 30000, status: "available" },
  dm_shop:         { title: "Магазин в директе",    group: "Instagram", price: 25000, status: "available", requires: ["instagram"] },
  broadcasts:      { title: "Рассылки",             group: "База",     price: null, status: "available" },
  multi_currency:  { title: "Мультивалютность",     group: "Каталог",  price: 18000, status: "available" },
  robokassa:       { title: "Онлайн-эквайринг",     group: "Оплата",   price: 25000, status: "available" },
  receipt_ocr:     { title: "Распознавание чека",   group: "Оплата",   price: 20000, status: "available" },
  legal_docs:      { title: "Юридические страницы", group: "База",     price: null, status: "available" },
  courses:         { title: "Курсы",                group: "Каталог",  price: 18000, status: "planned" },
  coupons:         { title: "Скидки и промокоды",   group: "Оплата",   price: 20000, status: "planned" },
  referral:        { title: "Реферальная программа", group: "Удержание", price: 14000, status: "planned" },
  // …остальное из прайса добавляется сюда же по мере готовности
} as const satisfies Record<string, ModuleDef>;
```

Правила:
- `status: "planned"` — модуль есть в прайсе, кода нет. В панели показывается
  серым, «в разработке», включить нельзя. Это честная дорожная карта: видно,
  что продано авансом, а что готово.
- `price` берётся из `Прайс-лист v8` и используется в панели как подсказка при
  разговоре с клиентом.
- Реестр — **единственный** источник списка модулей. Ни в панели, ни в
  миграциях списки ключей руками не дублируются.

### Как добавить новый модуль (то, ради чего всё)

1. Запись в `MODULES` со `status: "available"`.
2. Код фичи, обёрнутый в `hasModule("ключ")` — серверная часть, и
   `useModules()` — клиентская.
3. Деплой.

После этого тумблер появляется в панели у всех пяти клиентов автоматически.
Включение — одно нажатие, без правок кода и без передеплоя клиента.

## 4. Флаги времени выполнения (замена сборочных)

Сейчас `src/lib/feature-flags.ts` читает `VITE_FEATURE_*` — это **сборочные**
константы, вшиваемые в бандл. Переключение требует правки переменных Vercel и
пересборки. Требование «одна кнопочка» так не выполняется. Заменяем.

**Сервер** — `src/lib/modules/modules.server.ts`:

```ts
let cache: { at: number; row: BotRow } | null = null;
const TTL = 60_000;

async function loadBot(): Promise<BotRow> {
  if (cache && Date.now() - cache.at < TTL) return cache.row;
  const s = await db();
  const { data } = await s.from("bots")
    .select("status, modules, paused_message")
    .eq("id", process.env.BOT_ID!).single();
  cache = { at: Date.now(), row: data! };
  return data!;
}

export async function hasModule(key: ModuleKey): Promise<boolean> {
  const { modules } = await loadBot();
  return (modules as Record<string, boolean>)?.[key] === true;
}
export async function botStatus(): Promise<"active" | "paused" | "suspended"> { … }
```

Кеш на 60 секунд, в памяти процесса. Одно чтение строки обслуживает и модули, и
статус бота. «Включил — заработало в течение минуты» — приемлемо; мгновенно
сделает опциональный сброс кеша из §5.

**Клиент.** Модули нужны и на клиенте (навигация админки, гарды роутов).
Отдавать их через loader корневого роута `__root.tsx`, класть в контекст
роутера, читать хуком `useModules()`. Существующий `LockedNavLink` уже написан
и переиспользуется — меняется только источник значения.

**`feature-flags.ts` удаляется**, вместе с `VITE_FEATURE_*` в `.env.example`.
Это откат моей же недавней правки: сборочные флаги были верным шагом для «один
репозиторий, разные деплои», но требование одной кнопки они не закрывают.

## 5. Действия, требующие токена бота

«Остановить бота», «написать владельцу от имени бота» — казалось бы, нужен
токен клиента в панели. Не нужен, и лучше без него.

**Остановка бота — вообще без токена.** `bots.status` читается тем же кешем в
`handleUpdate`, сразу после проверки блокировки:

```ts
const st = await botStatus();
if (st !== "active") {
  await tg("sendMessage", { chat_id, text: await pausedMessage() });
  return;
}
```

Вебхук остаётся на месте, Telegram не трогаем — бот просто вежливо отвечает,
что временно недоступен. Возобновление — снятие флага, тоже без Telegram.
Текст ответа настраивается в панели (`bots.paused_message`), чтобы можно было
различать «профилактика» и «приостановлено за неоплату».

**Сообщение владельцу — через внутренний API клиента.** Каждый клиентский
деплой поднимает:

```
POST /api/internal/notify-owner
Header: x-internal-secret: <bots.internal_secret>
Body:   { text: "…" }
```

Обработчик сверяет секрет, берёт **свой** `TELEGRAM_BOT_TOKEN` из своих же
переменных окружения и отправляет. Панель знает `bots.app_url` и
`bots.internal_secret` — токена не знает и знать не должна.

Почему так, а не «положить токены в `bots.bot_token`»: утечка базы панели тогда
означает потерю пяти ботов целиком — чужие переписки, рассылка спама от имени
клиента, смена вебхука на сторонний сервер. Через внутренний API утечка секрета
даёт максимум возможность отправить сообщение — неприятно, но обратимо и
локально.

**Тот же эндпоинт закрывает и сброс кеша:** `POST /api/internal/reload`
обнуляет кеш модулей. Тогда переключение тумблера действует мгновенно, а не
через минуту.

**Фаза 0 обязана очистить `bots.bot_token`** — сейчас там живой токен
Анастасии. Столбец либо удалить, либо занулить; он нигде в коде не читается
(проверено).

### 5.1. Где живут токены ботов — разобранный вопрос

Вопрос возникает сам собой: «может, всё-таки хранить токены в базе, как-нибудь
безопасно?» Разобрано, решение — **не хранить**, и вот почему.

Отправная точка: любая операция, требующая токена, — это операция **над ботом
конкретного клиента**. А деплой этого клиента токен уже держит, законно и по
необходимости: без него бот не работает вовсе. Значит панели токен не нужен —
нужен способ попросить деплой сделать действие. Это и есть внутренний API.

Сейчас так закрыты все четыре операции:

| Операция | Кто делает | Токен у панели |
|---|---|---|
| Написать владельцу | деплой, `/api/internal/notify-owner` | не нужен |
| Сбросить кеш модулей | деплой, `/api/internal/reload` | не нужен |
| Проставить вебхук | деплой, `/api/internal/set-webhook` | не нужен |
| Проверить, жив ли бот | деплой, `/api/internal/health` | не нужен |

Побочная выгода у `set-webhook`: адрес берётся из `PUBLIC_APP_URL` самого
деплоя, а не из того, что оператор набрал в панели. Ошибиться доменом нельзя
в принципе.

**Что рассматривалось и отвергнуто.**

*Открытым текстом в `bots.bot_token`.* Так было до Фазы 0. Утечка базы панели
= потеря пяти ботов целиком: чужие переписки, рассылка спама от имени клиента,
смена вебхука на сторонний сервер. Цена ошибки несоразмерна удобству.

*Шифрование в базе (AES-256-GCM, ключ в переменных панели).* Заметно лучше
открытого текста: утечки одной только базы недостаточно, нужен ещё доступ к
переменным окружения панели. Но выигрыша над внутренним API нет — тот, кто
получил переменные панели, и так может дёргать её серверные функции, — а
плата есть: управление ключом, его ротация, новая поверхность атаки. Строить
преждевременно.

**Что за это не покрыто — честно.** Если деплой клиента мёртв или удалён,
панель до токена не дотянется. Восстановление — через BotFather (`/token`,
при компрометации `/revoke`), доступ к которому есть у владельца. Это
приемлемо: сценарий редкий, а выход из него существует и не требует, чтобы мы
постоянно держали у себя пять ключей от чужих ботов.

**Когда решение стоит пересмотреть.** Если появится задача, где панель должна
действовать токеном в момент, когда деплой недоступен. Пока такой нет:
мониторинг «жив ли бот» устроен наоборот — недоступность деплоя и есть тот
самый сигнал, ради которого мониторинг заводят.

При подключении клиента токен всё же проходит через панель — один раз,
транзитом: `getMe` для проверки и вывод в блоке переменных. В базу он при этом
не попадает, в журнал `bot_events` — тоже (там только username бота).

## 6. Связь с владельцами — через их собственных ботов

**Решение владельца:** когда оператор пишет одному, нескольким или всем
клиентам, сообщение приходит клиенту **от его собственного бота**. Отдельный
бот оператора не заводим.

Значит канал ровно один — внутренний API из §5, и никакого
`OPERATOR_BOT_TOKEN` в панели не появляется. Панель не хранит ни одного
токена Telegram вообще.

```
Панель → POST {bots.app_url}/api/internal/notify-owner
         header x-internal-secret: {bots.internal_secret}
         body   { text }
              ↓
   деплой клиента берёт СВОЙ TELEGRAM_BOT_TOKEN
              ↓
   сообщение владельцу от его же бота
```

`bots.owner_telegram_id` всё равно нужен — это `chat_id`, куда деплой шлёт.
Владелец почти всегда уже есть в `bot_users` своего бота (он его
администратор), поэтому заполняется один раз при подключении клиента.

Следствия, которые надо учесть в реализации:

- **Рассылка по всем — это N HTTP-запросов к N деплоям**, а не один вызов
  Telegram. Делать последовательно с таймаутом на каждый, результат по
  каждому клиенту показывать отдельно.
- **Лежащий деплой = недоставленное сообщение.** Панель обязана показать это
  явно («не доставлено: деплой не ответил»), а не молча проглотить. Логировать
  в `operator_broadcasts` статус по каждому получателю.
- **Автоуведомления** (истекает подписка, бот не отвечает) идут тем же путём.
  Если деплой не отвечает — уведомить об этом надо уже оператора, в самой
  панели, а не клиента.

## 7. Изменения схемы БД

### `bots` — добавить

| Колонка | Тип | Зачем |
|---|---|---|
| `app_url` | text | адрес деплоя; для внутреннего API и ссылок в панели |
| `internal_secret` | text | аутентификация внутреннего API (§5) |
| `owner_telegram_id` | bigint | кому писать от бота оператора |
| `owner_name` | text | как зовут владельца |
| `owner_contact` | text | телефон/почта |
| `paused_message` | text | что бот отвечает в паузе |
| `notes` | text | ваши заметки по клиенту |

`settings` (jsonb, уже существует, сейчас пуст) — поведение при неоплате,
см. §10.

`status` расширить до `active | paused | suspended` (CHECK-ограничение).
`bot_token` — занулить или удалить (§5).
`modules` — нормализовать (§8).

### Новые таблицы

**`bot_events`** — журнал действий оператора. Кто, когда, что переключил.
Не роскошь: при пяти клиентах и растущем числе модулей «почему у него это
выключено» станет частым вопросом.
```
id, bot_id, at, actor, kind ('module_on'|'module_off'|'pause'|'resume'|'onboard'|'message'), payload jsonb
```

**`operator_broadcasts`** — что и когда рассылали владельцам, кому дошло.

**`subscription_payments`** (Фаза 6) — `bot_id, period_start, period_end,
amount, currency, paid_at, note`. Прайс делает подписку обязательной, значит
нужен ответ на «кто оплачен до какого числа». Отсюда же автоматическое
`suspended` при просрочке.

### RLS — обязательно

`bot_events`, `operator_broadcasts`, `subscription_payments` — **запретить роли
`tenant_bot` полностью**. По умолчанию новая таблица без политик недоступна
никому, кроме `service_role` — этого достаточно, главное не выдать грант по
привычке.

По `bots`: у арендатора остаётся политика «видит только свою строку». Он
увидит свой `internal_secret` — это нормально, его деплой и так им владеет.
Чужие строки закрыты, как и раньше.

## 8. Фазы

Порядок обязателен: Фаза 0 — предохранитель, без неё Фаза 1 ломает живых
клиентов.

### Фаза 0 — предохранители (миграция, кода не трогает) ✅ ВЫПОЛНЕНО

1. Составить реестр (§3) и по нему нормализовать `bots.modules` у всех пяти:
   полный канонический набор ключей, значения — **как есть у клиента
   сегодня**. Сверять не с прошлыми намерениями, а с фактом:

   | Клиент | vip | instagram | blocked | broadcasts | robokassa | receipt_ocr | legal_docs |
   |---|---|---|---|---|---|---|---|
   | Анастасия | ✗ | ✓ | ✗ | ✓ | ✓ | ✓ | ✓ |
   | Салтанат | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ |
   | Print KZ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ |
   | Дидактика | ✓ | ✗ | ✓ | ✗ | ✗ | ✗ | ✗ |
   | Развивашка | ✓ | ✓ | ✓ | ✗ | ✗ | ✗ | ✗ |

   Таблица составлена по наличию кода и значению `feature-flags.ts` в каждом
   репозитории **до** слияния. **Эта опора уже устарела — перепроверить
   обязательно.**

   После перевода на общий репозиторий у каждого клиента физически есть код
   всех модулей: VIP, Instagram, RoboKassa, распознавание чеков. «Наличие
   кода» больше никого не различает — различают только флаги. И пока флаги
   сборочные, деплой без своих `VITE_FEATURE_*` берёт значения по умолчанию
   из кода, а они выставлены под Анастасию.

   Это уже происходит: проект `saltanat-material` собран из объединённого
   репозитория, переменных `VITE_FEATURE_*` у него нет, поэтому он унаследовал
   `instagram: true` — значение, выбранное для другого клиента. Правильный
   набор для каждого определяется не кодом, а тем, **что клиент оплатил**;
   сверять с прайсом и с вами, а не с репозиторием.

2. Занулить `bots.bot_token`.
3. Добавить колонки и таблицы из §7.
4. Заполнить `app_url` пятью известными адресами, сгенерировать
   `internal_secret`.

### Фаза 1 — флаги времени выполнения ✅ ВЫПОЛНЕНО

`registry.ts`, `modules.server.ts`, загрузка в `__root.tsx`, `useModules()`.
Удалить `feature-flags.ts` и `VITE_FEATURE_*`. Перевести на новый источник:
навигацию `admin.tsx`, гард `admin.instagram.tsx`, добавить гарды VIP и
блокировки. Проверка: у каждого клиента набор вкладок не изменился.

### Фаза 2 — панель, минимум ✅ ВЫПОЛНЕНО

Роуты `/operator/*`, отдельная сессия, guard из §2. Экраны:
- **Клиенты** — список, статус, подписка до, ссылка на деплой, заметки.
- **Карточка клиента** — тумблеры модулей из реестра (сгруппированные, с
  ценами, `planned` серым), пауза/возобновление, журнал событий.

Уже на этом этапе выполняется главное требование: модуль включается флажком.

### Фаза 3 — связь ✅ ВЫПОЛНЕНО

Внутренний API (`notify-owner`, `reload`) на клиентском деплое, экран рассылки
по владельцам (одному / выбранным / всем), журнал доставки с результатом по
каждому получателю. Бот оператора не нужен — §6.

Реализовано. Исходы доставки различаются четырьмя статусами, каждый со своей
причиной: `sent`, `failed` (деплой ответил и отказал — виден его текст ошибки),
`unreachable` (не достучались: таймаут 10 с, DNS, лежащий деплой), `skipped`
(не заполнен `app_url` или `internal_secret` — это незаполненная карточка, а не
сбой). Проверено на живых деплоях: все четыре исхода отрабатывают и попадают в
`operator_broadcasts.results`.

Осталось на будущее: рассылка идёт синхронно, N запросов подряд по 10 с
таймаута. На пяти клиентах это максимум ~50 с — приемлемо. При росте до
десятков клиентов упрётся в лимит времени серверless-функции, и её придётся
переводить в очередь, как сделано с `broadcasts` для покупателей.

### Фаза 4 — подключение клиента, полуавтомат

Мастер: имя, токен от BotFather, домен, набор модулей. Панель создаёт строку
`bots`, счётчик заказов, выпускает `SUPABASE_TENANT_KEY`, проставляет вебхук,
и **выдаёт готовый блок переменных для вставки в Vercel**. Проект Vercel
создаёте руками.

Сознательно останавливаемся здесь: `VERCEL_TOKEN` не сужается по правам и даёт
доступ ко всем проектам аккаунта, включая чтение переменных. Полчаса ручной
работы раз в пару месяцев — приемлемая плата за то, чтобы этот токен не лежал
в веб-приложении.

### Фаза 5 — полная автоматизация (по желанию)

Создание проекта Vercel из API. Делать, только если Фаза 4 реально начнёт
раздражать. Панель к этому моменту должна быть за Deployment Protection.

### Фаза 6 — деньги и наблюдение — СДЕЛАНО (кроме статистики заказов)

`subscription_payments` (MIGRATION-09) — источник истины про «оплачен до»;
`bots.subscription_expires_at` пересчитывает триггер, руками не правится.
Платежи, политика при неоплате и состояние подписки — в карточке клиента,
состояние вынесено и в список. Ежедневный обход
(`/api/operator-cron/subscriptions`, внешний планировщик) предупреждает за
`warn_days_before` и применяет `on_overdue` после `grace_days`;
идемпотентность — по маркеру периода в `bot_events`, чтобы клиент не получал
одно и то же каждые сутки. «Отвечает ли бот» — кнопкой «Проверить бота»
(§5.1), токен для этого панели не нужен.

Показатели по клиентам — MIGRATION-10, функция `operator_bot_stats()`:
заказов за 30 дней и всего, дата последнего заказа, товаров, покупателей,
занятое место в хранилище (считается по ссылкам из таблиц арендатора на
`storage.objects`). Видно и в списке, и в карточке; давнее «последний заказ»
подсвечивается — молчащий бот и есть главный признак, что что-то сломалось.

**Какие срезы пускать в панель — решено: только агрегаты.** COUNT, MAX(дата),
SUM(байт) и ничего больше: ни названий товаров, ни имён покупателей, ни сумм
заказов. Оператору нужно знать, что клиент жив и растёт, а не что он кому
продаёт. То, что service_role технически видит всё, — не основание показывать
всё. Расширять состав — отдельное решение.

### Фаза 6 (исходная формулировка)

Подписки и платежи, авто-`suspended` при просрочке. Мониторинг: заказов за
месяц по каждому, дата последнего заказа, занятое место в хранилище, отвечает
ли бот. Это то, ради чего панель открывают ежедневно, — подключение клиента
случается пять раз в год.

## 9. Что проверить на каждой фазе

- После Фазы 1 у каждого из пяти клиентов **набор вкладок в админке и
  поведение бота не изменились**. Это главный критерий: рефакторинг флагов
  обязан быть незаметным.
- Клиентский деплой отвечает 404 на `/operator` и на прямой вызов любой
  серверной функции оператора. Проверять curl'ом, не глазами.
- Тумблер модуля у клиента А не влияет на клиента Б.
- Пауза бота: бот отвечает текстом из `paused_message`, заказы не создаются,
  админка клиента продолжает работать.
- Внутренний API отклоняет запрос с чужим или отсутствующим секретом.

## 10. Решённые вопросы

**Рассылка клиентам — от их собственных ботов.** Отдельного бота оператора
нет, см. §6. Панель не хранит токенов Telegram.

**Поведение при неоплате — настройка, а не решение в коде.** Ни «всегда
отключать», ни «всегда только предупреждать». Хранить в `bots.settings`:

```jsonc
{
  "on_overdue": "warn",      // "warn" | "suspend"
  "warn_days_before": 5,     // за сколько дней предупредить
  "grace_days": 3            // сколько терпеть просрочку до suspend
}
```

Значение по умолчанию — `warn` (мягкое). Переключатель в карточке клиента,
плюс возможность задать значение по умолчанию для новых клиентов. Реализуется
в Фазе 6 вместе с подписками, но поле завести сразу в Фазе 0, чтобы потом не
трогать схему.

**Замочки некупленных модулей — оставляем как есть, но это временно.**
Текущий `LockedNavLink` — заглушка. В планах **магазин модулей внутри
клиентской админки**: клиент видит каталог того, что можно подключить, с
описанием и ценой, и оставляет заявку. Отдельная фаза, проектировать
отдельно.

Реестр модулей (§3) уже готов к этому: поля `title`, `group`, `price` в нём
заведены именно под будущую витрину, а не только для панели оператора. При
реализации магазина брать данные оттуда же — второго списка модулей быть не
должно.
