# Анализ проекта tg_bot

Обследование от 2026-08-16. Проверено против живой базы и живого хранилища,
а не только по коду: каждый пункт ниже подтверждён запросом или запуском.

Секретов в этом документе нет и быть не должно.

---

## Что это за проект

Мультиарендная платформа Telegram-магазинов на TanStack Start (React 19,
Vite 8, Nitro) поверх Supabase. Один репозиторий разворачивается в шесть
проектов Vercel: пять клиентских ботов и одна панель оператора
(`CONTROL_PLANE=1`), различаются они только переменными окружения.

Арендаторы в базе (все `active`, план `pro`, кроме демо):

| Клиент                             | Деплой                      | Ключей в `modules` |
| ---------------------------------- | --------------------------- | ------------------ |
| Educational Bot                    | aatech-pi.vercel.app        | 14                 |
| SALTANAT \| Материалы для педагога | saltanatmaterial.vercel.app | 14                 |
| Print KZ Art                       | printkzart.vercel.app       | 14                 |
| DID 02                             | didaktika03.vercel.app      | 14                 |
| Развивашка                         | razvivashkakaz.vercel.app   | 14                 |
| Демо-тестер (free)                 | dem-teaster.vercel.app      | 35                 |

Объём данных: 86 МБ база, 12,3 ГБ хранилище, 3314 пользователей ботов,
489 заказов, 484 товара, 369 VIP-подписок.

## Что сделано правильно

Это стоит зафиксировать, потому что дальше идёт список проблем.

**Изоляция арендаторов работает по-настоящему.** RLS включён на всех 30
таблицах `public`. Политики единообразные: `bot_id = current_bot_id()` плюс
отдельная политика для `service_role`. Пять таблиц панели (`bot_events`,
`operator_broadcasts`, `operator_login_attempts`, `subscription_payments`)
идут с RLS и нулём политик — то есть закрыты для всех, кроме `service_role`,
и это правильно, а не упущение.

Проверено не только глазами: `tests/tenant-isolation.test.ts` ходит в
настоящую базу настоящим ключом арендатора. С заданными переменными
окружения проходит весь набор — **42 теста из 42**, включая 7, которые в
обычном прогоне пропускаются.

**Фаза 0 из `CONTROL-PLANE-PLAN.md` выполнена.** План предупреждал, что в
`bots.bot_token` лежит рабочий токен Telegram. Сейчас `bot_token` = `NULL`
во всех шести строках, `internal_secret` проставлен везде — панель ходит в
клиентские деплои через `/api/internal/*`, как и задумано.

**`payment-proofs` закрыт правильно.** Чеки покупателей не отдаются
публично (проверено: запрос без ключа → HTTP 400), политики только для
`service_role`.

**Индексы под мультиарендность на месте.** 25 из 27 таблиц с `bot_id`
проиндексированы по нему — RLS-фильтр не приводит к последовательному
сканированию.

**Документация решений выше среднего.** `DEPLOYMENT.md`,
`CONTROL-PLANE-PLAN.md`, комментарии в `modules.server.ts` и
`require-module.server.ts` объясняют _почему_, а не только _что_. Отдельно
ценно, что там записаны и известные ловушки (замаскированные значения в
интерфейсе Vercel, отсутствие `.env.example` и причина этого).

## Критическое

### 1. Платные материалы скачиваются кем угодно без оплаты

Бакет `product-files` — **публичный**. В нём 647 файлов на 12 ГБ: это то,
что покупают клиенты всех пяти арендаторов.

Подтверждено эмпирически:

- анонимным ключом (`SUPABASE_PUBLISHABLE_KEY`) успешно перечисляется
  содержимое бакета через `POST /storage/v1/object/list/product-files` —
  возвращаются реальные имена файлов;
- по полученному имени файл скачивается **вообще без каких-либо ключей**:
  `GET /storage/v1/object/public/product-files/<имя>` → `HTTP 200`,
  `content-type: application/pdf`.

Анонимный ключ при этом не секрет — он по определению лежит в браузерном
бандле каждого клиентского деплоя (`VITE_SUPABASE_PUBLISHABLE_KEY`). То
есть перечислить и выкачать весь каталог платных материалов может любой,
кто открыл любой из магазинов.

Это обходит оплату у всех арендаторов сразу и ломает файловую изоляцию
между ними: имена в бакете общие, префикса `bot_id` в них нет.

**Код к закрытию уже готов — менять надо только флаг бакета.** Все пути
выдачи файлов покупателю не зависят от публичности:

- `src/lib/orders.server.ts:340` — `createSignedUrl(path, 7 дней)`, ссылка
  отдаётся Telegram, чтобы тот скачал сам;
- `src/lib/orders.server.ts:380` — `supabaseAdmin.storage.download()`,
  сервер-сайд под `service_role`;
- `src/lib/zernio-bot.server.ts:525` — снова `createSignedUrl`;
- `src/routes/api/admin/file/$.ts` — проксирование под админской сессией.

`getPublicUrl` во всём проекте вызывается ровно один раз и для другого
бакета — `instruction-videos` (`src/lib/bot.server.ts:315`). На
`product-files` публичный доступ не опирается ничто.

Починка — снять с бакета `public` и убрать политику `Public Read
product-files`:

```sql
update storage.buckets set public = false where id = 'product-files';
drop policy if exists "Public Read product-files" on storage.objects;
```

Подписанные ссылки, выданные до этого, продолжат работать до истечения
своих семи дней — выдача покупателям не прервётся.

Отдельно стоит решить по `product-images` (567 файлов, 290 МБ): он тоже
публичный, но там витринные картинки, и цена вопроса другая. Проверять его
надо вместе с `src/routes/api/public/img/$.ts`, который их проксирует.

## Высокое

### 2. Одиннадцать из четырнадцати «готовых» модулей — тумблер без замка

`src/lib/modules/registry.ts` объявляет 35 модулей, 14 из них со статусом
`available`. Комментарий в самом файле определяет статус так: «available —
код есть и проверен, **тумблер работает**».

На деле флаг модуля читается кодом только для трёх из них:

| Модуль      | Где проверяется                                            |
| ----------- | ---------------------------------------------------------- |
| `vip`       | `requireModule("vip")` ×3, `hasModule("vip")` в вебхуке    |
| `blocked`   | `requireModule("blocked")`                                 |
| `instagram` | `requireModule("instagram")`, `hasModule` в вебхуке Zernio |

Остальные одиннадцать — `shop`, `broadcasts`, `multi_files`,
`order_status`, `excel_export`, `legal_docs`, `robokassa`, `receipt_ocr`,
`multi_currency`, `multi_language`, `dm_shop` — не проверяются нигде: ни
`requireModule`, ни `hasModule`, ни `useModules()`. Переключение их в
панели оператора не меняет поведение деплоя ни на сервере, ни в интерфейсе.

Практический смысл: выключить клиенту `robokassa` или `receipt_ocr` за
неоплату сейчас нельзя — эквайринг и распознавание чеков продолжат
работать. Ровно ту дыру, которую `require-module.server.ts` закрыл для VIP
(и подробно описал в своей шапке), для остальных модулей не закрыли.

### 3. Реестр и база разошлись, а отсутствующий ключ читается как «выключено»

`loadModules()` в `src/lib/modules/modules.server.ts` устроен так:

```ts
result[key] = modules?.[key] === true;
```

Ключа нет в строке — модуль выключен. Это осознанное решение, оно
задокументировано. Но в базе у всех пяти живых арендаторов в `modules`
лежит **14 ключей из 35**, тогда как у демо-клиента — все 35.

Чего живым клиентам не хватает, притом что реестр считает это готовым:

- `order_status` — кнопка «📋 Мои заказы», группа «База», цена `null`
  (входит в пакет без доплаты);
- `excel_export` — выгрузка заказов и базы клиентов, тоже «База», `null`;
- `multi_language` — русский/казахский интерфейс, 16 000 ₸.

Сегодня это безвредно ровно потому, что верно пункт 2: гардов на эти
модули нет, флаг никто не читает. Но эти два пункта — заряженная связка.
В тот день, когда кто-то добросовестно добавит `requireModule("excel_export")`,
базовая функция молча пропадёт у всех пяти платящих клиентов. Это тот самый
сценарий, о котором предупреждает `CONTROL-PLANE-PLAN.md`: «каждое
расхождение станет пропавшей функцией у живого клиента».

Правильный порядок — сначала бэкфилл `modules` до канонических 35 ключей
всем арендаторам, и только потом расстановка гардов.

## Среднее

### 4. `zernio_logs` растёт без ретенции и уже занимает базу целиком

62 МБ из 86 МБ всей базы — это 72 %. 26 719 строк за 17 дней
(31.07 → 16.08), около **1670 строк в сутки**. Ни чистки, ни партиционирования
нет. При текущем темпе это ~610 тыс. строк и больше гигабайта за год, причём
99,7 % из них — `status = 'processed'`, то есть уже отработанные и
неинтересные (ошибок за весь период `0`).

Второй по темпу — `ig_poll_runs`, 7452 строки, 5,2 МБ.

Просится ретенция вроде «удалять `processed` старше 30 дней» отдельной
задачей крона — механизм крона в проекте уже есть
(`/api/cron/*`, `CRON_SECRET`).

### 5. Шестнадцать ошибок TypeScript, и это не устаревшие типы

Первое подозрение — что типы БД отстали — проверено и снято: запуск
`scripts/sync-db-types.mjs` против живой базы отвечает «всё уже совпадает».
Значит, все 16 ошибок настоящие:

| `src/lib/bot.server.ts`           | 4      |
| `src/lib/zernio.server.ts`        | 2      |

Разбираются они на три группы:

- **`Record<string, unknown>` против `RejectExcessProperties`** (3 шт.) —

- **сужение `Json`** (`bot.server.ts:211-213`) — из `settings` читается

  девять функций; вызываются кодом две, объявлена одна. Комментарий в
  `types.ts` честно говорит, что блок ведётся руками, а
  `sync-db-types.mjs` переносит только таблицы, — но `increment_broadcast_counts`
  туда просто забыли дописать.

### 6. Линтер: 2598 замечаний, из них ~230 содержательных

`pnpm lint` даёт 2590 ошибок, но 2363 из них — форматирование, которое
чинится `--fix`: prettier давно не прогоняли. За вычетом шума остаётся:

- **223 × `@typescript-eslint/no-explicit-any`**;
- **2 × `react-hooks/rules-of-hooks`** — единственное здесь, что тянет на
  настоящий рантайм-баг, а не на стиль. Стоит посмотреть отдельно и первым;
- 2 × `prefer-const`, 1 × `no-irregular-whitespace`;
- **1 parsing error** — файл целиком не разбирается линтером, то есть

Форматирование лучше вычистить одним отдельным коммитом, иначе оно и
дальше будет прятать содержательные замечания.

### 7. Два лок-файла в репозитории

Отслеживаются одновременно `package-lock.json` и `pnpm-lock.yaml`. Какое
дерево зависимостей уедет в прод, зависит от того, чем ставит CI, и эти два
дерева не обязаны совпадать. Нужно выбрать один менеджер и удалить
второй файл; судя по наличию `pnpm-lock.yaml` и рабочей команде
`pnpm install --frozen-lockfile`, выбор — pnpm.

### 8. Мелочи

- **`search_products` — мёртвая миграция.** Функция заведена
  `MIGRATION-07-search-products.sql` и живёт в базе, но `.rpc("search_products")`

## Сделано по итогам обследования

Пункты 1, 2, 3, 5 и 6 из списка выше закрыты в этой же ветке.

**Бакет `product-files` закрыт.** Проверено после изменения: скачивание
без ключей — было `HTTP 200`, стало `HTTP 400`; перечисление анонимным
ключом — было списком имён, стало пустым; политика `Public Read
product-files` удалена. Обе легитимные ветки выдачи проверены живьём и
работают: подписанная ссылка → `HTTP 200`, server-side download под
`service_role` → `HTTP 200`.

**`rules-of-hooks` оказались ложными.** `useSession` — серверный хелпер
TanStack Start, а не React-хук; плагин опознаёт его лишь по имени на
`use*`. Правило снято с `*.server.ts`, код не тронут.

Зато рядом нашлось настоящее: **`scripts/set-webhook.mjs` не запускался
вовсе** — тот самый parsing error. В файл с расширением `.mjs` попала
аннотация типа, и Node падал на ней с `SyntaxError`. Именно этот скрипт
`DEPLOYMENT.md` называет способом поставить вебхук. Заодно убран
запасной адрес на чужой деплой, который молча увёл бы вебхук не туда.

**`tsc` проходит начисто**, все 16 ошибок разобраны. Устаревшие типы БД
как причина проверены и исключены.

**`MIGRATION-16`: `modules` приведены к 35 ключам** у всех шести
арендаторов. `multi_language` расставлен по факту наличия казахского
контента, а не на глаз. Ни один включённый ранее модуль не потерян —
счётчики сошлись с расчётными.

**Ретенция `zernio_logs`** живёт внутри `/api/cron/broadcast`
(`src/lib/zernio-logs.server.ts`), порог задаётся
`ZERNIO_LOG_RETENTION_DAYS`. Важно понимать: **сегодня она не удалит
ничего** — самой старой записи 16 дней при пороге в 30. Это профилактика,
базу она уменьшит не раньше конца августа. Поэтому ветка удаления
проверена отдельным тестом на своих же строках
(`tests/zernio-logs-retention.test.ts`), а не оставлена «до первого раза».

Тестов стало 44, проходят все.

**Осталось нетронутым:** пункт 4 (гарды на оплачиваемые модули —
это решение продуктовое, а не техническое), пункт 7 (форматирование и
223 × `any`) и пункт 8 (второй лок-файл). Плюс открытый вопрос по
`product-images`.

# Второе обследование: недостающий функционал и ошибки

Отдельный проход, уже по другому вопросу: чего в проекте нет и что в нём
ломается. Сборка проверена — `vite build` проходит.

## Мёртвая схема: Instagram-автоматизация прошлого поколения

Семь таблиц не упоминаются в коде **ни одной строкой** — только в
сгенерированном `types.ts`:

| Таблица              | Строк | Назначение                       |
| -------------------- | ----- | -------------------------------- |
| `ig_poll_runs`       | 7452  | прогоны опроса со статистикой    |
| `ig_comment_actions` | 4     | действия по комментариям         |
| `ig_post_leads`      | 2     | лиды с машиной состояний ретраев |
| `ig_watched_posts`   | 2     | отслеживаемые посты              |
| `ig_keywords`        | 1     | правила «ключевое слово → ответ» |
| `ig_exclusions`      | 0     | отписки                          |
| `zernio_automations` | 0     | локальная копия автоматизаций    |

Вместе они описывают целую самостоятельную систему Comment-to-DM: опрос
по расписанию, ретраи с `next_retry_at` и `retry_until_at`, `closed_reason`,
`debug_info`. Причём построенную на **другом провайдере** — в
`ig_post_leads` есть столбец `unipile_comment_id`, а слова «unipile» в
репозитории нет вовсе.

История читается по датам: опрос работал с 27.07 по 01.08 — 7452 прогона,
за которые просмотрено 252 комментария и отправлено 16 DM. Первая запись в
`zernio_logs` — 31.07. То есть подход сменили на вебхуки Zernio, код опроса
удалили, а таблицы и 5,2 МБ данных остались.

Это не ошибка, но это мусор, который выглядит как рабочая часть системы:
следующий, кто откроет схему, потратит время на выяснение, почему
`ig_poll_runs` не пишется. Удалять — отдельным решением, данные всё-таки
чужие.

## Ошибка: застрявшие события Instagram теряются навсегда

69 записей в `zernio_logs` висят в статусе `pending` — обработка началась и
не завершилась ничем: ни `processed`, ни `error`.

Разбор вебхука (`src/routes/api/public/zernio/webhook.ts`) объясняет как:
обработка уходит в `runInBackground` через `waitUntil`, и если инстанс
свернули раньше, чем задача дошла до записи статуса, не выполнится ни
ветка успеха, ни `catch`. Строка остаётся `pending` навсегда.

Хуже то, что **перечитывать их некому**. Кода, который брал бы `pending` и
пробовал заново, в репозитории нет (проверено поиском по всем обращениям к
таблице). А Zernio на такое событие получил `200` и повторять не будет.
Значит, за каждой из 69 строк стоит сообщение или комментарий клиента в
Instagram, на который никто не ответил и уже не ответит.

# Третье обследование: сверка интеграции Zernio с документацией

Проверено по официальной документации Zernio. Четыре расхождения, все
исправлены; каждое ниже — с тем местом доков, которое его определяет.

## 1. Дедупликация не работала, и это второй DM клиенту

Доки: доставка **at-least-once**, до 7 попыток, «your handler must
therefore be idempotent», и рекомендованный приём — вставлять идентификатор
события в таблицу с уникальным индексом и пропускать обработку при
конфликте.

Было наоборот: сначала `SELECT` по `event_id`, потом отдельный `INSERT`.
Две одновременные доставки одного события обе не находили строку, обе
вставляли, нарушение уникального индекса `zernio_logs_bot_event_id_key`
уходило в `console.error` — **и обработка продолжалась в обеих**. Для
клиента это второе одинаковое сообщение в Direct.

Что подтверждает, что это не теория: в таблице **11 941 лишняя строка**
(45 %) — 4627 групп с повторяющимися `event_id`. Разбор одной группы:
событие `00133c7c-…` (`comment.received`) обработали три разных бота —
Educational Bot, Развивашка и Print KZ Art — с разницей в 6 секунд.

Отдельная хорошая новость: по датам видно, что межарендаторная часть уже
вылечена. Дубли есть только 12–14 августа (30–60 % в день) и ровно ноль до
11-го и после — коммит `90a2b82 fix: isolate Instagram webhooks by profile`
закрыл именно это. Сам фильтр по профилю написан верно и падает закрыто.

Теперь конфликт вставки и **есть** ответ «уже принято»: первая доставка
держит строку, остальные уходят с 200, ничего не обрабатывая. Заодно
исправлено поведение при других ошибках записи: раньше событие
обрабатывалось даже когда записать его не удалось (то есть без всякой
защиты от повтора) — теперь это `500`, и Zernio повторит по своему
расписанию, как доки и предполагают.

## 2. Подписка на события, которых мы не обрабатываем

Доки, первым же пунктом: «Subscribe only to the events you actually
handle».

Подписка была на десять событий при двух обработчиках, и один из двух —
`handleZernioComment` — состоял из `console.log`. Комментарии закрывают
родные Comment-to-DM автоматизации Zernio, наше участие там не нужно.

Чего это стоило:

| Событие             | Строк  | Доля   | Обработчик |
| ------------------- | ------ | ------ | ---------- |
| `comment.received`  | 19 088 | 69,2 % | заглушка   |
| `message.received`  | 7886   | 28,6 % | есть       |
| `message.read`      | 309    | 1,1 %  | нет        |
| `message.sent`      | 292    | 1,1 %  | нет        |
| `account.connected` | 10     | 0,0 %  | нет        |

То есть **69 % всего трафика вебхука и объёма логов существовало ради одной
строчки в консоли** — а `zernio_logs`, напомню, это 62 МБ из 86 МБ базы.

Подписка сведена к `message.received`, заглушка удалена. Дашборд не
пострадал: статистику по комментариям он берёт из `rule.stats` в ответе
Zernio, а не из наших логов (`getInstagramDashboardFn`).

`account.disconnected` намеренно не подписан. Событие полезное — истёкший
токен означает, что бот молча перестаёт отвечать, — но обработчика у него
нет, и подписываться на него надо вместе с обработчиком, а не заранее.
Это следующая осмысленная задача по Instagram.

> **Требует действия руками.** Список событий хранится на стороне Zernio.
> Деплой сам его не переоформит — нужно нажать «Обновить Webhook» в
> админке (Instagram) на каждом клиенте, где включён модуль.

## 3. Исходящий вызов Zernio внутри 5-секундного бюджета

Доки: доставка успешна, если эндпоинт ответил `2xx` **в течение 5 секунд**;
иначе повтор. И отдельным предупреждением: «Keep your handler fast».

`isInstagramAccountInConfiguredProfile` на каждом входящем событии звала
`listZernioAccounts`, а та — `GET /accounts` к самому Zernio, без кеша. При
~1670 событиях в сутки это столько же лишних round-trip'ов, и все внутри
того самого бюджета.

Добавлен кеш состава профиля на минуту. Пустой ответ и ошибка не кешируются
— иначе разовый сбой Zernio погасил бы обработку на всю минуту. Изоляция от
этого не страдает: чужой аккаунт в кеше появиться не может.

## 4. Отправка без `Idempotency-Key`

Доки описывают заголовок `Idempotency-Key` именно для этого случая: тот же
ключ с тем же телом возвращает исходный ответ вместо второй отправки, ключ
живёт сутки.

Мы его не передавали. Само по себе это уже не бьёт по клиенту — после
пункта 1 повторная доставка отсеивается раньше, — но остаётся обязательным
условием для добора застрявших событий, о котором ниже.

Ключ выводится из идентификатора события и тела запроса, а идентификатор
проносится через обработку в `AsyncLocalStorage`
(`src/lib/zernio-event-context.server.ts`). Так сделано потому, что отправка
вызывается из 24 мест: протаскивать параметр через всю цепочку значило бы
поменять 24 сигнатуры и надеяться, что в новом коде о нём вспомнят.

Семантика важна в обе стороны, поэтому закрыта тестами
(`tests/zernio-idempotency.test.ts`): повтор того же события даёт тот же
ключ, разные события с тем же текстом — разные, разные сообщения внутри
одного события — разные, а вне обработки события ключа нет вовсе, иначе
подавлялась бы законная ручная отправка из админки.

## Что по Zernio осталось несделанным

- **Добор застрявших `pending`.** 69 событий висят необработанными и никем
  не перечитываются (см. второе обследование). Теперь, когда отправка
  идемпотентна, добор можно делать безопасно — но это изменение поведения,
  а не уборка, поэтому отдельной задачей.
- **Обработчик `account.disconnected`** — превратить молчаливую смерть бота
  в видимую.
- **`buttons` в приватных ответах на комментарии.** Доки прямо
  предупреждают: `quickReplies` не отображаются в папке Message Requests,
  куда попадают DM от неподписчиков, и для холодного охвата нужны
  `buttons`. `sendInstagramPrivateReply` сейчас шлёт только текст.
- **Мёртвые таблицы `ig_*`** из прошлого поколения — решение об удалении.

# Четвёртое обследование: вся Instagram-часть

Разбор всех 3050 строк Instagram-кода против документации Zernio, плюс
дизайн и редактура экрана.

## Профиль подписчика не собирался ни разу

Самое дорогое из найденного. `handleZernioMessage` читал профиль
отправителя из `payload.data.instagramProfile`. Поля `data` Zernio не
присылает **вовсе** — его нет ни в одном из 26 865 сохранённых событий, а
профиль лежит в `message.sender.instagramProfile`, и по докам, и по факту.

Итог: у **всех 1175 пользователей Instagram** `metadata` пустая. Ни одной
записи `isFollower`, `followerCount` или `isVerified` — при том что колонку
под них завела отдельная миграция `PATCH-IG-USER-METADATA.sql`, где прямо
написано «из Zernio».

Ошибка из тех, что не видит никто: типы молчали (`payload: any`), линтер
молчал, при чтении диффа код выглядит правильным — он просто читает не
оттуда. Ловится только сверкой с настоящим событием.

Тип `ZernioWebhookMessagePayload` описывал ту же выдумку: объект `data` с
плоскими `senderId`, `senderUsername`, `commentText`. Приведён к настоящей
схеме, разбор вынесен в чистую функцию `parseZernioMessage` и закрыт
тестами на форме, скопированной из настоящей записи `zernio_logs`.

Данные о старых диалогах задним числом не появятся — они не сохранились
нигде. Собираться начнут с ближайшего входящего сообщения.

## Тело запроса к автоматизациям

**`null` вместо пропуска поля.** Для правила «на все посты» доки
предписывают _опустить_ `platformPostId` и `postId`; форма отдавала явный
`null`, и он уходил как значение. Теперь пустые поля вычищаются — но
аккуратно: пустая строка сохраняется (ею оператор очищает публичный ответ,
иначе поле не очистить никогда), пустой список ключевых слов тоже (по докам
это «срабатывать на любой комментарий»). Разница закрыта тестами.

**Длина DM не проверялась.** Доки: `dmMessage` обязателен, максимум 640
символов при заданных кнопках (сообщение становится `button_template`) и
около 1000 без них. Раньше Zernio отвечал `400` уже после нажатия
«Сохранить», и оператор видел сырую английскую ошибку. Теперь проверяем у
себя и объясняем по-русски, что именно сократить.

# Пятое обследование: магазин в Instagram Direct (19 коммитов после четвёртого раунда)

С прошлого обследования (`951187c`) в ветку легла отдельная фича — покупка
прямо в переписке: корзина, выбор страны, чек, почта, автовыдача. Это
`src/lib/direct-purchase.server.ts` (новый, 1046 строк) и переписанный
`src/lib/zernio-bot.server.ts` (1421 → 1461 строк), плюс `pricing.server.ts`,
`mail.server.ts`, `product-materials.ts`. Каждый коммит в этой серии чинит
конкретный живой инцидент, и это видно по комментариям в коде — культура
обследования, заданная в первых четырёх раундах, выдержана. Ниже — то, что
не поймано их собственной живой проверкой.

## Гонка: два сообщения подряд создают два заказа из одной корзины

Весь сценарий покупки хранит шаг диалога в `bot_users.state` (jsonb) по схеме
«прочитать → изменить → записать»: `setDirectState`, `addToCart`, `readCart` +
`clearCart`, `handleStepMiss` — везде отдельные `select`, потом отдельный
`update`, без единого атомарного условия между ними
(`src/lib/direct-purchase.server.ts:97-134, 761-831`). Ровно тот паттерн,
из-за которого дедупликация вебхука ловила «второй одинаковый DM» (раздел
третьего обследования, пункт 1) — только починили его там, а не здесь.

Критичный момент — шаг ожидания чека
(`handlePurchaseFlow`, `src/lib/zernio-bot.server.ts:966-1086`):

1. приходит вложение → `storeReceipt` (скачивание + загрузка в Storage,
   сетевые вызовы);
2. `createOrderFromCart` — читает корзину, создаёт `orders` + `order_items`;
3. только после этого `clearCart` и смена `state.mode` на `awaiting_email`
   (или сброс, если чек сразу распознан).

Между шагом 1 и записью нового `state.mode` в шаге 3 проходит реальное время
— два похода в сеть и минимум три запроса к базе. Если за это время придёт
**второе** сообщение с вложением от того же человека (а не повтор доставки
одного и того же вебхук-события — с этим уже разобрались), второй запрос
Vercel обработает его параллельно первому: прочитает тот же `state.mode ===
"awaiting_proof"`, ту же корзину, ещё не очищенную, и создаст **второй
заказ с тем же составом**. Дедупликация по `event_id`
(`zernio_logs_bot_event_id_key`) здесь не спасает — это не повторная
доставка, а два разных события с двумя разными вложениями.

Это не гипотетический пользователь. В переписках, разобранных в предыдущих
раундах, люди уже присылали чек дважды подряд «на всякий случай» — под это
специально написана ветка на шаге `awaiting_email` (строки 1120–1164:
«пришла ещё одна картинка вместо адреса — это второй чек, а не ошибка»). Она
работает только если первое сообщение успело смениться на
`awaiting_email` **до того**, как пришло второе. Стоит второму прийти чуть
раньше — и вместо «прикрепим чек к тому же заказу» получится дублирующий
заказ, второе уведомление продавцу с кнопками «Подтвердить/Отклонить», а при
совпадении суммы — двойная автовыдача (два одинаковых письма покупателю).
Ничего не теряется и не рвётся, но продавец получает лишний заказ, который
придётся распознать как дубль руками, а покупатель — два письма вместо
одного.

Чинится тем же приёмом, что уже есть в проекте для похожей задачи —
`claimOrderForDelivery` в `orders.server.ts` берёт заказ в работу через CAS
(`update ... where status = X`, а не «прочитал, потом записал»). Здесь
нужен аналог: например, атомарно перевести `state.mode` из `awaiting_proof`
в промежуточное `processing_proof` перед тем, как начинать `storeReceipt`, и
проверять это условие в `update`, а не читать `state` заранее.

## Тестов на эту часть нет

`tests/direct-flow.test.ts`, `tests/pricing.test.ts`, `tests/product-materials.test.ts`
проверяют только чистые функции разбора текста и расчёта цены — и делают это
хорошо. Но код, который трогает деньги и базу
(`createOrderFromCart`, `handlePurchaseFlow`, вся приёмка чека и автовыдача в
`zernio-bot.server.ts`), тестами не покрыт вовсе. Гонка из пункта выше
тестом не поймать без мока конкурентных запросов, но само отсутствие
покрытия на самой рискованной части — это отдельный, более общий пробел.

## Мелочь: чеки разных арендаторов лежат в одной папке

`storeReceipt` кладёт чек по пути `${user_key}/....`, где `user_key` —
`ig_<sender_id>` (`src/lib/zernio-message.ts:57`), то есть идентификатор
Instagram-профиля покупателя, без привязки к арендатору. Бакет
`payment-proofs` один на все шесть деплоев (комментарий в
`client.server.ts`: «Storage is deliberately excluded: buckets are shared»).
Если один и тот же человек в Instagram написал и купил у двух разных клиентов
этой платформы, его чеки из обеих покупок лягут в одну и ту же папку общего
бакета. Утечки нет — доступ к `payment-proofs` только у `service_role`, и
выдача всегда идёт по точному пути, сохранённому в заказе своего арендатора,
— но граница между клиентами в самой раскладке файлов стёрта, и это может
аукнуться, если когда-нибудь появится инструмент вида «показать все чеки
этого покупателя» на общем хранилище.

## Что стоит сделать по итогам

1. Заблокировать шаг `awaiting_proof` от повторного входа, пока обрабатывается
   первое вложение (CAS по аналогии с `claimOrderForDelivery`) — единственный
   пункт с реальным пользовательским сценарием позади.
2. Добавить хотя бы один тест на `createOrderFromCart`/`handlePurchaseFlow` с
   моком Supabase — сейчас самая денежная часть кода ничем не защищена от
   регресса.
3. Опционально: включить `bot_id` или префикс арендатора в путь
   `storeReceipt`, чтобы папка в общем бакете не была общей между клиентами.

## 215 × `@typescript-eslint/no-explicit-any` — до нуля

Разобрано по файлам, от крупных к мелким, с проверкой `tsc --noEmit` +
`vitest run` + `eslint --fix` на каждом коммите. В подавляющем большинстве
случаев `any` был лишним: Supabase-запрос уже возвращает типизированную
строку из сгенерированных `types.ts` (`.select("*")` или именованный
эмбед), а `any`/`as any` просто маскировал это и не давал компилятору
проверить остальной код. Такие случаи — снятие каста без изменения
поведения.

Отдельно от механической части — несколько мест, где `any` скрывал
настоящие расхождения между тем, что код предполагает, и тем, что
реально возвращает база или внешний API:

* **`bot.server.ts` (`handleUpdate`)** — `chat_id` доставался через
  опциональную цепочку и использовался как гарантированный `number`;
  добавлен `if (!chat_id || !cq.from) return;`.
* **`vip-bot.server.ts` (`handleVipUpdate`)** — та же форма бага: и в
  message-, и в callback_query-ветке `chat_id`/`from` считались
  гарантированными, хотя у Telegram Update оба поля опциональны.
  Добавлены ранние `return` в обеих ветках.
* **`vip-member.server.ts` (`getMemberAssignedTariff`)** — вручную сужал
  `vip_tariffs(*)` до трёх полей (`id`/`is_active`/`is_public`), хотя
  запрос уже тянет всю строку; `showStartFlow` в `vip-bot.server.ts`
  добирался до `price`/`currency`/`name` только через `as any` поверх
  этого урезанного типа. Лишний ручной каст снят.
* **`zernio-bot.server.ts` (`upsertZernioUser`)** — ветка на ошибку
  вставки возвращала объект без поля `email`, хотя дальше по сценарию
  Direct-покупки `user.email` читается для автовыдачи при сошедшемся
  чеке. Раньше это маскировал `any`; добавлено `email: null` в
  fallback-литерал, как у настоящей свежевставленной строки.
* **`zernio.server.ts` (`ZernioConversation.participantId`)** — при
  прошлой типизации `listZernioConversations`/`getInstagramContactProfilesFn`
  обнаружилось, что `admin.instagram.tsx` читал `conversation.participantId`
  под `any`, хотя такого поля в ответе `/inbox/conversations`, возможно,
  никогда не было. Поле добавлено с явной пометкой «не проверено против
  живого ответа Zernio» — это не подтверждённый фикс, а честно
  задокументированная неопределённость: показ «подписчик / не подписан»
  в Direct-переписке мог не работать никогда, и без доступа к
  `ZERNIO_API_KEY` в этой сессии проверить нельзя.
