# Объединение репозиториев — исходные данные и план

Документ для следующего этапа: свести пять клиентских репозиториев к одному
ядру. Здесь зафиксировано состояние на момент завершения переезда на общую
базу — что уже сделано, насколько репозитории разошлись (измерено, а не на
глаз), где грабли и в каком порядке разумно идти.

---

## 1. Где мы сейчас

Все пять ботов работают на одной базе Supabase (`fnwksbasxakktscdjlfp`).
Изоляция сделана в Postgres, а не фильтрами в коде: у каждого деплоя свой
ключ с зашитым `bot_id`, RLS отсекает чужие строки, триггер проставляет
`bot_id` при вставке — подделать из приложения нельзя (проверено).

| Клиент | Репозиторий | `bot_id` | Счётчик заказов |
|---|---|---|---|
| Анастасия | `tg_bot` | `0bac1f86-5231-4e57-838d-2faa44d427e7` | 426 |
| Салтанат | `saltanat_materials_bot` | `de44b934-c8db-47ac-9aa9-535c762cf8c7` | 7 |
| Print KZ | `print_kz_art` | `89d155d1-91e1-4c2d-981e-43741a0badc3` | 7 |
| Дидактика | `did_02` | `19ce949b-8877-4fa7-b072-c09980eb7ee3` | 27 |
| Развивашка | `razvivashka` | `d6331748-52e2-4b88-af41-ccd545f789a8` | 0 |

Ключи `SUPABASE_TENANT_KEY` намеренно **не** записаны в этот файл — они дают
доступ к данным клиента. Живут только в переменных окружения Vercel; при
необходимости выпускаются заново командой:

```
SUPABASE_JWT_SECRET=… node scripts/mint-tenant-key.mjs <bot_id>
```

Старые базы клиентов не удалены и лежат как страховка.

### Главный вывод: это не пять веток одного кода, а две линии

**Линия A — `tg_bot`.** Совпадает с остальными ровно наполовину. У него есть
14 файлов, которых нет больше нигде: рассылки, эквайринг RoboKassa, проверка

файлов, которые есть у всех четверых остальных. `bot.server.ts` вдвое больше
(2060 строк против ~1015).

**Линия B — `saltanat`, `print_kz`, `did_02`, `razvivashka`.** Между собой
близки: salt↔print 92%, print↔razv 86%. Ядро из 76 файлов одинаково у всех
четверых. У всех есть VIP-подписки, блокировки пользователей, отдельный
VIP-вебхук.

`did_02` — исключение внутри линии B (65–69%), потому что у него **нет
Instagram-модуля**: `zernio.server.ts`, `zernio-bot.server.ts`,
`instagram.functions.ts`, `admin.instagram.tsx` и вебхук Zernio. Это и есть
почти весь его разрыв с остальными.

## 3. Подход: объединение множеств

Собираем **все** наработки из всех пяти репозиториев в одно ядро. Не
выбираем репозиторий-победитель: каждая возможность, которая есть хоть у
одного клиента, попадает в общий код. Там, где реализаций несколько, берётся
самая свежая и полная — новые проекты богаче фичами и содержат меньше старых
болячек, потому что каждый следующий делался на базе предыдущего.

Домом становится репозиторий `tg_bot`: там уже лежат миграции, скрипты
выпуска ключей и генератор типов.

Пофайловая раскладка — что откуда берём — в `MERGE-MAP.md`. Коротко: из 129
файлов настоящего слияния требуют **девять**, остальное механика. Самый
тяжёлый — `bot.server.ts`, где у Анастасии 2060 строк против ~1015 у
остальных, потому что её модули перемешаны с общей логикой магазина.

Уникальные модули (рассылки, эквайринг, распознавание чека, юридические
страницы, VIP, Instagram) включаются флагами в `bots.modules`. Колонка уже
существует и заполнена по факту использования, схема БД одинакова у всех
арендаторов — миграции не нужны, только флаг.

Клиентов переводим по одному, в порядке возрастания риска: Развивашка и
Дидактика, затем Print KZ и Салтанат, последней — Анастасия с её 426
заказами.

Один репозиторий и пять проектов Vercel: несколько проектов могут смотреть в
один репозиторий, у каждого свои переменные и домен. Чтобы плохой коммит не
ложил всех разом, выкат держим ступенчатым — один проект на `main`,
остальные на `release`, которую перематываете, убедившись, что всё живо.

## 4. Грабли, на которые уже наступили

Список не гипотетический — всё перечисленное происходило.

**Переменные окружения нельзя переключать раньше кода.** Случилось дважды.
Старый `client.server.ts` не знает про `SUPABASE_TENANT_KEY` и подключается
под `service_role`, который обходит RLS. Результат — админка клиента
показывает данные всех. Порядок обязателен: **сначала мерж и успешный
деплой, потом переключение переменных.** Защита от этого теперь есть в коде
(деплой падает, если `BOT_ID` задан без tenant-ключа), но она сама должна
быть сначала задеплоена.

**Функции и RPC не переезжают вместе с таблицами.** `search_products` жила
только в базах клиентов; после переезда её не стало, и поиск у `saltanat` не
работал несколько недель. Восстановлена в `MIGRATION-07`.
**`increment_broadcast_counts` до сих пор отсутствует** — вылезет, когда
кто-то включит рассылки.

**Ошибки RPC в коде не проверяются.** Шаблон `const { data } = await
s.rpc(...)` встречается повсеместно: ошибка молча превращается в `null`, и
бот отвечает «ничего не нашлось» вместо сбоя. При объединении это стоит
починить разом — иначе следующая пропавшая функция снова будет искаться
неделями.

**Покупателю показывается `order_no`, а не `orders.id`.** Последовательность
`orders.id` общая на всю базу; у нового клиента первый заказ получил бы номер
вроде 449. Нельзя вызывать `reset_orders_sequence` — она откатывает общую
последовательность. При подключении клиента счётчик ставится на его текущий
максимум, иначе нумерация у покупателей поедет назад (ловили на Print KZ).

**`category_ids` — это `jsonb`, а не `uuid[]`.** Фильтр должен быть
`.contains("category_ids", JSON.stringify([id]))`. С формой для массива
PostgREST отвечает ошибкой, и товары в категории просто не находятся.

**`bot_id` теперь без `DEFAULT`.** Раньше стоял временный дефолт с id
Анастасии — деплой с забытым `BOT_ID` молча писал данные в её базу. Снят в
`MIGRATION-06`; теперь такая вставка падает с NOT NULL.

**Уникальные индексы должны включать `bot_id`.** Один и тот же тестовый
Telegram-аккаунт в двух ботах ломал перенос. Разобрано в `MIGRATION-04` —
при добавлении новых уникальных индексов помнить про это.

**Бакеты Storage общие.** Сброс данных нельзя делать обходом бакета
(`walk("")` снесёт файлы всех клиентов). Удалять только пути, названные
строками своего арендатора — как сделано в текущем `reset.functions.ts`.

**`bots.bot_token` под UNIQUE.** Двум ботам одинаковую заглушку не поставить.

## 5. Открытые хвосты

- `increment_broadcast_counts` — RPC отсутствует в общей базе.
- Типы: `razvivashka` — 21 ошибка компиляции, `tg_bot` — около 17. Почти всё
  это давняя типизация Zernio, на работу не влияет, но при слиянии всплывёт.
- Ветка `claude/instagram-deleted-post-crosscheck` не смержена и не удалена.
- Старые базы пяти клиентов не удалены (страховка).
- JWT-секрет проекта светился в переписке. При плановой ротации все
  tenant-ключи придётся выпустить заново — удобнее сделать это до
  подключения следующего клиента, а не после.

## 6. Что стоит решить до начала

**Где живёт кастом клиента.** Пока это не определено, «общее ядро» будет
разъезжаться заново. Варианты: флаги в `bots.modules` (для модулей),
переменные окружения (для деплоя), отдельная папка `clients/<name>/` в общем
репозитории (для настоящих индивидуальных доработок). Первые два уже
существуют, третьего нет.

**Что делать с `tg_bot`.** Либо втягивать в общее ядро (дорого, но один код),
либо признать его отдельным продуктом с рассылками и эквайрингом и вести
параллельно. Решение лучше принять до шага 1, потому что от него зависит,
куда складывать общие куски.
